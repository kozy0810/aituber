# 3Dモデル生成ツールの調査結果

調査日: 2026-09-16 〜 2026-09-17
ステータス: **一次情報または実機で確認済みの事項のみを記載**

配信用キャラクターモデルを生成するツールとして、Meshy と Tripo を比較検証した結果。検討中・未確定の論点は `tmp/tool-research.md` 側に残してある。

## 結論

**Meshy を採用する。開発・検証では Meshy 6 Lite を使う。**

四足など非人型の体型に対応でき、無料枠でダウンロードと商用利用(CC BY 4.0、帰属表示が必要)まで可能なため。ただし**非人型のリギングはWeb UIでしか実行できない**という制約がある。

## Meshy と Tripo の比較

| 観点 | Meshy | Tripo |
|---|---|---|
| Web UIでの非人型リギング | ○ | ○ |
| **API/MCPでの非人型リギング** | **✗ 人型専用** | **○ 7生物タイプを`rig_type`で指定可** |
| 公式MCP | ○(Proプラン以上が必要) | ○(アルファ版) |
| 無料プランでのダウンロード | ○ Meshy 6 Lite のみ・月10回 | ✗ プラン契約が必須 |
| 無料プランでの商用利用 | ○ CC BY 4.0(帰属表示が必要) | ✗ 有料プランの機能 |

### 根拠となった一次情報

**MeshyのリギングAPIは人型専用。**

> "programmatic rigging currently only works well with standard humanoid (bipedal) assets with clearly defined limbs and body structure"

> "Currently, auto-rigging is not suitable for the following models: Untextured meshes, Non-humanoid assets, Humanoid assets with unclear limb and body structure"

パラメータは `input_task_id` / `model_url` / `height_meters` / `texture_image_url` の4つのみで、体型を指定する手段が存在しない。MCPの `meshy_rig` はこのAPIのラッパーであるため同じ制約を受ける。

**この制約はMeshy自身のAIエージェントによって独立に裏付けられた。** パンダの画像を渡して四足リギングを依頼したところ、次の回答が返った。

> 現在のリギング機能は**二足の人型スケルトン専用**で、パンダのような四足動物には対応していません。四足歩行として動かせる形にはならない点、あらかじめお伝えします。

同じ回答の中で、モデルバージョンについても重要な事実が判明した。

> 画像→3Dモデル生成ツールで選べるのは「meshy-6」と「meshy-7」のみで、**「Meshy 6 Lite」という個別モデルは選択肢にありません**

つまり **Meshy 6 Lite はWeb UI限定で、API/MCP/エージェントからは使えない**。無料でダウンロードできる唯一のモデルがAPI経由で使えないため、**API経由では無料プランで成果物を取り出せない**ことになる。

結論として、Meshyの自動化経路には二重の制約がある。

| | Web UI | API / MCP / エージェント |
|---|---|---|
| 非人型のリギング | ○ | ✗ |
| Meshy 6 Lite(無料DL可) | ○ | ✗ |

**Tripoの`rig_type`は7生物タイプに対応**(biped / quadruped / hexapod / octopod / avian / serpentine / aquatic)。出力はリグ済みGLBまたはFBXで、ボーン命名はTripo独自形式かMixamo互換を選択できる。

**Tripoは無料プランでエクスポートできず、商用利用も有料プランの機能**(実機でアップグレードモーダルを確認)。APIの残高は実測で0であり、Web版のサブスクリプションとAPIクレジットは別勘定。

## リップシンクの実現方式

**顎ボーンの回転を音声振幅に連動させる方式を想定している。** ビセーム(口の形のブレンドシェイプ)は使わない。

理由: MeshyもTripoも顔のブレンドシェイプを自動生成しない。Meshyは「詳細な顔リグ(顎・目・口の制御)は Blender や Maya での手作業」と明言している。一方で、**「四足歩行イヌ科」リグのマーカー一覧には「顎」が標準で含まれる**ことをUIで確認した。リップシンクに必要なのは顎ボーン1本であり、この経路なら成立する。

この方針により、**TTSに音素・ビセームデータの出力を要求する必要がなくなった**。音声の振幅さえ取れればよいため、TTSは音質・コスト・日本語品質で自由に選べる。

### 結論: Meshyの自動リギングでは顎ボーンが得られない(検証完了)

両方のリグ経路で実際にGLBを書き出し、解析して確認した。

| リグ経路 | 参考画像の姿勢 | ジョブ結果 | ボーン名 | **顎ボーン** |
|---|---|---|---|---|
| 四足歩行イヌ科 | 座り・四肢密着 | **失敗** | — | — |
| スマートリグ (Beta) | 座り・四肢密着 | 成功 | `Bone_000`〜 の無名連番 | **なし** |
| 四足歩行イヌ科 | **立ち・四肢が離れる** | **成功** | 意味のある名前 | **なし** |

#### 立ち姿勢で得られたリグ(27ボーン)

```
Hips
├ chest → head → headend / earend / R_earend
├ tail → tailstart → tail1 → tail2 → tail3
├ backleg → backleg0 → backleg1 → backleg2   (左右)
└ frontleg → frontleg0 → frontleg1 → frontleg2 (左右)
```

歩行アニメーション(81チャンネル)も同梱され、**四足の体の動きとしては実用的**。しかし頭部にあるのは `head` / `headend` / 左右の `earend` のみ。

**リギングUIで「顎」マーカーを配置したにもかかわらず、書き出されたリグに顎・口のボーンは存在しない。** 顎マーカーは頭ボーンの位置決めに使われるだけで、独立した顎ボーンを生成しない。

モーフターゲットも0個(両経路とも)。

#### より深い問題: メッシュに口の形状が存在しない

顎ボーンの不在よりも根本的な制約が、生成メッシュの解析で判明した。

**生成されたメッシュには口の開口部がない。** 顔の正中線に沿って前面のZ座標を高さごとに測ると、鼻先から額まで**滑らかな凸曲線**を描き、凹みが一切現れない。口はテクスチャに描かれているだけで、立体としては存在しない。

```
高さ(Y)      最前面Z    プロファイル
0.0069(鼻先) 0.0079    ####################################### ← 最も前
0.0074       0.0074    ##################################
0.0083       0.0073    ##################################
0.0089       0.0069    #############################
0.0092(額)   0.0054    #############                          ← 後退
```

口を閉じた写真から生成しているため当然の結果だが、これは**リグの問題ではなくジオメトリの問題**であり、影響範囲がはるかに広い。

さらにテクスチャは自動生成のUVアトラスで島が細かく断片化しており、顔がまとまった領域として配置されていない。テクスチャ空間で口を差し替える手法も取りにくい。

#### 影響: リップシンクの実装方針を根本から選び直す必要がある

口の立体が存在しないため、**ボーンを足しても頂点を動かしても「口が開く」表現にはならない**。顎ボーンを回せば、開口部のない顔の下半分が飴のように伸びるだけで破綻する。当初の「顎ボーン+音声振幅」案も、その代替として挙げた「頂点変形」案も、この一点で同時に成立しなくなる。

実装しうる選択肢は次の通り。

| 案 | 内容 | 自動化 | 難点 |
|---|---|---|---|
| A. 口を開けた参考画像から生成 | 口が開いた状態の画像を使えば口腔の立体が生成される。その後に顎ボーンを追加して可動させる | 高 | 常に半開きの造形になる。閉口時の見た目に影響 |
| **B. headボーンに板を取り付ける** | 口を描いた板(quad)を3D空間でheadボーンに親子付けし、音声振幅で開き具合を変える | **高** | 3Dモデルに描かれた口と二重に見えないようにする必要がある |
| C. Blenderで口を造形 | 口のシームを切り、内側を作り、顎ボーンを入れる。本格的な3Dモデリング作業 | 低 | キャラ1体ごとに人手の作業が発生 |
| D. 体型アーキタイプ方式 | 口を含めて作り込んだベースモデルを体型ごとに用意し、外見だけ転写する | 中 | 体型ごとの初期構築が必要。任意体型という要件と衝突 |
| E. 口を動かさない | 頷き・耳の動き・体の揺れなど、口以外の動きで「喋っている」ことを表現する | 最高 | 視聴者の期待に応えられるかは要検討 |

### 採用: 案B(headボーンに親子付けした板)

**画面上に2Dとして合成するのではなく、3D空間内に板を置いてheadボーンの子にする。** この違いは実装量に直結する。

- 画面空間で合成する場合、頭の位置を毎フレーム投影し、頭が向こうを向いたら隠すという判定を自前で書く必要がある
- **3D空間に板を置けば、位置・回転・前後関係・遮蔽はすべてレンダラーが処理する**。頭が回れば板も一緒に回り、後ろを向けば自然に見えなくなる

#### 取り付け位置は自動で求まる(検証済み)

案BがC・Dより優れているのは、**キャラクターごとの人手作業が一切要らない**ため。取り付け位置はリグ済みGLBから機械的に導出できることを実機で確認した。

1. `frontleg` と `backleg` ボーンの位置関係から**顔の向き**を判定する
2. `head` ボーン近傍(メッシュ最大寸法の25%以内)の頂点のうち、**最も前方にあるものが鼻先**
3. そこが板の取り付け位置

実測結果(立ち姿勢パンダのGLB):

```
顔の向き   : +Z
アンカー座標: (0.0000, 0.0064, 0.0083)
BBox内の相対位置: X=50.0%  Y=65.1%  Z=100.0%
```

**Xがちょうど50%**(正中線上)、**Zが100%**(メッシュ最前面)に乗っており、鼻先として妥当。人手のクリックも、キャラごとの設定ファイルも要らない。

この導出は `.claude/skills/generate-character-model/scripts/inspect_glb.py` に実装済みで、GLBを渡せばアンカー座標と板の寸法目安が出力される。

#### 注意: 寸法は必ずメッシュ寸法比で指定する

**モデルは極端に小さいスケールで書き出される。** 実測したGLBの最大寸法は `0.0167` しかなかった。板のサイズ・オフセット・変形量を絶対値で書くと、別のキャラクターでは見えないか巨大になる。すべてバウンディングボックスに対する比率で表現すること(目安として板は最大寸法の6〜8%)。

#### 二重の口を避ける

3Dモデルのテクスチャにも口が描かれているため、板と重なって二重に見える恐れがある。これは**参考画像の生成時に決まり、後工程では直せない**。画像生成のプロンプトで口を目立たせないよう指定しておく(手順は skill の手順1を参照)。

### 影響しない範囲

この制約は**口の動きに限った話**。体の動き(歩く・向きを変える・頷く・耳を動かす)は得られたリグで問題なく制御できる。`head` ボーンがあるため視線方向や頷きも実装できる。

## 利用規約上の注意

MeshyのAcceptable Use Policyは、スクリプトによる一括・自動アップロードを含む**無許可の自動化プロセスを禁じている**。

> "Using unauthorized automated or scripting processes (such as bulk or automated uploading of content through a script)"

Web UIを大量に自動操作してAPI課金を回避する運用はしない。自動化が必要になった段階で、正規のAPI/MCP(Proプラン)を契約する。

## 参考画像に関する要件(実機で確認)

- **1体だけが写った画像にする。** front/side/back が1枚に並んだ三面図をそのまま渡すと、被写体が並んだまま1つのメッシュになる
- **背景と小道具はメッシュに取り込まれる。** 参考画像に写っていた鉢植え・草・台座が、キャラクターと一体のメッシュとして生成された
- **四肢が体から離れた姿勢が必要。** 座って四肢が密着した姿勢では、四足リグ(`四足歩行イヌ科`)が**失敗する**(品質低下ではなくジョブ失敗)。同じモデルで**スマートリグ(Beta)は成功した**

詳細な手順は `.claude/skills/generate-character-model/` を参照。
