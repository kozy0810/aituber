# ヘッドレスレンダリングと配信の調査結果

調査日: 2026-09-17
ステータス: **一次情報で確認済みの事項のみを記載**(実装による検証は未実施)

サーバー上でキャラクターを24時間レンダリングし続け、YouTube Liveへ配信するための技術的な実現性調査。

## 結論

**実現可能で、既存の道筋がある。レンダリング性能はボトルネックにならない。**

## 全体の構成

```
three.js シーン(GLBモデル + ライティング)
    ↓ ヘッドレスGPUレンダリング
生のRGBAフレーム(gl.readPixels)
    ↓ 標準入力へパイプ
FFmpeg (-f rawvideo -pixel_format rgba -video_size 1920x1080 -framerate 30 -i pipe:0)
    ↓ h264_nvenc でGPUエンコード
RTMPS → rtmp://a.rtmp.youtube.com/live2/<stream key>
```

## レンダリング性能は問題にならない

node-webgl の実測値(Apple M5 Max)として、**PBR・影付きのthree.jsシーンが1フレームあたり0.18ミリ秒**でレンダリングされる。理論上5,500fps相当であり、必要な30〜60fpsに対して2桁の余裕がある。

キャラクター1体と簡素な背景という今回のシーン構成では、**3Dレンダリング自体は制約にならない**。

## 真の制約: パイプ帯域とエンコード

**1080p・RGBA・60fpsの生フレームは約498 MB/s**。これをプロセス間で転送し続けるため、メモリ帯域を大きく消費する。

**30fpsを採用すれば約249 MB/sに半減する。** YouTube自身が「静的なコンテンツ(トーク、ウェビナー)は低い方の設定を使う」と推奨しており、喋るキャラクターの配信はこれに該当する。**30fpsが妥当**。

エンコードは `h264_nvenc` によるGPUエンコードでリアルタイムの10〜50倍の速度が出る。NVENCはT4/L4/A10のいずれにも搭載されている。ただし**FFmpegがNVENC対応でビルドされている必要がある**(パッケージマネージャ標準のものは未対応のことが多い)。

## ライブラリ候補

### node-webgl

- Node.jsでGPUを使ったヘッドレスWebGL 1/2を実現。Chromeと同じレンダリングエンジン(ANGLE)を使用
- **three.jsが完全に動作する**。「同じレンダリングコードがブラウザとサーバーの両方で動く」と明記
- macOS(Metal) / Windows(D3D11) はプリビルド、**Linuxはインストール時にコンパイル**(約10秒、Mesa/Vulkan)
- フレーム取得: `gl.readPixels()`, `canvas.toBuffer('image/png')`, `getImageData()`
- **ライセンス要確認**: MITベースだが「AI Restriction」条項があり、AIシステムによる利用が原則禁止(公式three.jsリポジトリのみ例外)。**採用前に条項の適用範囲を確認すること**
- 制限: Canvas 2D非対応、HTMLVideoElement非対応、Linuxプリビルド未提供

### headless-three-webgpu

- Google Dawn 経由のWebGPUでthree.jsをヘッドレスレンダリング
- **フレームを生のRGBAとしてFFmpegへストリーム配信し、メモリ使用量を一定に保つ設計**。24時間配信の要件と合致する
- `--fps` `--duration` `--crf` `--codec` で調整可能。Dockerサポートあり。Node.js 24以上
- 制限: 環境マップは `.hdr` と `.ktx2` のみ、動画出力時は幅・高さが偶数である必要

### Godot(優先度低)

「headless(描画しない)」と「displayless(画面なしでGPU描画)」が区別され、後者の対応は限定的。FFmpegへのパイプ出力(NUT形式)は**提案段階で未実装**。three.js系より成熟度が低い。

## YouTube Live 側の要件

- **配信時間に制限はない。24時間配信は公式にサポートされている**
- ビットレート: 1080p/30fps は 3,000〜6,000 kbps、1080p/60fps は 4,500〜9,000 kbps
- プロトコルは **RTMPS**(RTMPの安全な拡張)が推奨
- **キーフレーム間隔は2秒**に設定する(4秒の上限を超えないため。0=自動は避ける)
- 1チャンネルあたり同時10配信、1ストリームキーあたり3配信まで

## GPUサーバーの費用(2026年9月時点の相場)

| GPU | 時間単価 | 月額(720時間換算) |
|---|---|---|
| A10 | $0.20〜 | **約$144〜**(約¥21,000〜) |
| L4 | $0.44〜0.90 | 約$317〜648 |
| T4 | 約$0.81 | 約$583 |

ハイパースケーラー(AWS/GCP等)よりneo-cloud系の事業者が40〜85%安い傾向。同じA10でも事業者により月$144〜$3,254と20倍以上の開きがあるため、**事業者選定がコストを大きく左右する**。

レンダリング負荷が極めて軽いことを踏まえると**最安クラスのGPUで十分**で、月額¥20,000〜30,000程度に収まる見込み。

### そもそもクラウドGPUを借りない選択肢がある

上記はクラウドでLinuxサーバーを借りる前提の試算だが、**Apple Silicon の Mac で動かせばGPUレンタルは不要になる。**

- エンコードは **VideoToolbox**(Apple Silicon搭載のハードウェアエンコーダ)が NVENC の役割を果たす
- node-webgl は **macOS arm64 向けのプリビルトが提供される**(Linuxはインストール時コンパイルが必要)
- AivisSpeech も macOS 版があり CPU で動作する

費用は月2万円規模から電気代(約560円)まで下がる。一方で冷却・可用性・回線帯域といった別の制約が発生する。

詳細な比較は `docs/deployment-options.md` を参照。
